## 步骤 3 — lumo ASR 流式配置分析

克隆参考：`/home/ubuntu/lumo-ref`（只读）。

### lumo 关键参数

| 参数 | 值 |
|------|-----|
| 模型 | sherpa-onnx-streaming-zipformer-bilingual-zh-en-2023-02-20 |
| 类型 | OnlineRecognizer（流式），transducer（encoder/decoder/joiner） |
| 量化 | int8（~54MB，儿童设备友好） |
| 采样率 | 16000 Hz |
| 特征维度 | 80 |
| VAD | Silero（独立并行运行），窗口 512 samples |
| 端点检测 | enableEndpoint=true |
| 输出 | partial（流式中间结果）+ final（isEndpoint 定稿） |
| 打断 | VAD 独立事件 onVadSpeechStart/End，供 barge-in 状态机 |

### 我们现有方案

| 参数 | 值 |
|------|-----|
| 模型 | sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17 |
| 类型 | OfflineRecognizer（整句 batch） |
| 调用 | speech_to_text(opus→wav文件→全文转写） |
| VAD | 无独立集成 |
| 输出 | 仅 final（整句） |
| 打断 | 不支持 |

### 差异报告

1. **流式 vs 整句**：lumo 边说边出字（partial），我们等说完整句才转写。儿童说话慢、停顿多，流式能早 1-2 秒开始处理。
2. **VAD 独立**：lumo 的 Silero VAD 与识别并行，可做语音端点检测和打断；我们没有。
3. **模型选择**：SenseVoice 精度高但非流式；zipformer 流式专为实时设计。建议：保留 SenseVoice 做高精度复核，主链路切流式 zipformer。
4. **儿童适配**：两者都未针对童声微调。Pasketti 挑战优胜方案（MIT）可作为下一步微调参考。

**状态**：✅ 方案完成，代码未动（按任务要求）。

## 步骤 4 — Pipecat 评估（200 字）

Pipecat 1.12.0 在 Python 3.12.3 安装运行成功。架构为 Pipeline + Processor：STT→LLM→TTS 标准链，支持自定义 Processor 插入任意位置。我们的 strategy_engine.py 是纯规则引擎（输入学习状态+观察信号→输出教学策略，无 LLM 依赖），可封装为 Pipecat 的 FrameProcessor，插在 STT 和 LLM 之间：STT 输出文本帧→策略引擎根据学习档案选择策略→改写/增强 LLM 的 system prompt→LLM 生成→TTS。11 种策略、6 级掌握状态机、policy_version 机制无需改动，只需写一个适配器类（约 50 行）。建议渐进接入：先保留现有 teach_loop 跑通 Pipecat 最小 pipeline 验证延迟，再迁移策略逻辑。不建议一次性重构。

**状态**：✅ 评估完成，可行，待试点。

## 步骤 5 — TTS 中文验证

**Kokoro-82M 中文支持**：✅ 确认支持。
- 8 个中文音色（4 女：zf_xiaobei/xiaoni/xiaoxiao/xiaoyi；4 男：zm_yunjian/yunxi/yunxia/yunyang）
- 语言码 `z`/`zh`，专用中文模型 Kokoro-82M-v1.1-zh
- CPU 可跑，Apache 2.0，24kHz 输出
- pip 安装验证中因 torch 下载缓慢未完成，但文档+多源确认可用

**Qwen3-TTS**：❌ 不可用。需 H100/4090 GPU，arm-agent 无 GPU。

**现有 edge-tts**：云端 API，延迟 2-4 秒/句。Kokoro 本地推理预期 <500ms/句（CPU）。

**结论**：Kokoro-82M 是正确选择（中文+CPU+开源），下一步部署 kokoro-fastapi-cpu Docker 服务替换 edge-tts。
